# Deployment status and prerequisites

The website has not been deployed. On 2026-11-22, all 20 repository migrations through `202611220019_rescheduled_reminders.sql` were applied to the configured hosted Supabase project. All 21 public tables have RLS enabled. The 2 pre-existing Auth users were preserved. Hosted rollback-only checks cover group isolation, group-creation permissions, expense proposals, manual payment confirmation, refunds, polls, weekly scheduling, receipt permissions/expiry and calendar management; no test business data persists. A separate Storage API smoke check verified private buckets, anonymous denial and physical deletion of its generated fixture. Full browser, concurrency and remaining feature acceptance checks are still pending.

1. Put the PostgreSQL owner connection in `SUPABASE_DB_URL`. Run `npm test`, then `npm run db:status` to inspect the target and pending migrations. `npm run db:migrate` applies pending files atomically and records Supabase-compatible history plus SHA-256 checksums. It refuses a mismatched project, unknown remote migration history or untracked existing schema. Never reset an existing remote project. Embedded tests do not require Docker; a full local Supabase stack does.
2. Configure the Supabase URL and publishable key from `.env.example`.
3. Enable Google OAuth in Supabase. Put Google client credentials in Supabase settings. Set the Google redirect to the Supabase auth callback; allow the app's `/auth/callback` URL in Supabase redirect settings.
4. Configure custom SMTP for email magic links. Default Supabase SMTP only delivers to project team members and is unsuitable for normal users. See https://supabase.com/docs/guides/auth/auth-smtp.
5. Set `NEXT_PUBLIC_APP_URL` to the actual application origin. Start with a Vercel Hobby `*.vercel.app` deployment. Run all checks and `npm run build` before publishing. Hosting credentials are not currently connected.
6. Complete remaining implementation and RLS acceptance tests before enabling production use. AI must remain disabled until per-group key encryption, approvals and live evaluations are complete.

Group setup: apply all SQL migrations in timestamp order after inspecting existing data. Set `SUPER_ADMIN_EMAILS` to comma-separated verified owner emails. `SUPABASE_SECRET_KEY` is required on the server only for group provisioning; obtain the secret key from the selected Supabase project's API settings. Group administration and invites use normal user sessions. After signing in as an allowed owner, open `/groups` to create the first group. Invitation URLs use `NEXT_PUBLIC_APP_URL`, so set the actual trusted origin before sharing. Do not add a wildcard redirect to Supabase Auth; permit the exact app callback origin/path. Account claims are reviewed by group admins in the group page.

Supabase Cron runs `3t-minute-maintenance` every minute and `3t-storage-cleanup` every five minutes; successful hosted executions have been verified. Inspect with `npm run db:cron`; install/update the minute job with `npm run db:cron:install`. Both call private SQL functions without public HTTP endpoints or cron secrets. The minute job's execution logs older than seven days are pruned; business history is retained. Web Push remains pending. Free Supabase has 500 MB database and 1 GB Storage; an internal cron does not guarantee avoiding automatic project pausing. See https://supabase.com/pricing and https://supabase.com/docs/guides/platform/free-project-pausing.

Session migrations: all files through `202611220019_rescheduled_reminders.sql` are applied on the configured hosted project. Future files must be added with a new version; do not edit applied SQL. The financial RPCs, approvals and transactional previews have embedded and hosted rollback-smoke coverage; browser end-to-end and concurrency checks are still required. Keep production use disabled until remaining permissions and approval workflows pass the complete handoff matrix. Expense writers, maintenance helpers and base history readers are private with client execution revoked; do not grant them to user roles.

Calendar acceptance: use separate creator, collector, ordinary member and group admin sessions. Verify authorized metadata edits, denied member edits, stale revision rejection, and unchanged balances. A future schedule change resets existing RSVP choices and prompts each person to self-confirm; an elapsed deadline cannot be reopened by editing metadata. Cancellation is permitted only with no nonzero expense history and no transfers; reopening needs a future deadline and fresh commitments. Check that only the selected weekly instance changes, notifications arrive, and repeated cron runs do not duplicate reminders for the same schedule generation. Admin financial fallback/unlock remains unavailable.

Storage setup: migrations create `3t-payment-evidence` and `3t-expense-receipts` as private, 2 MiB JPEG/PNG/WebP buckets. Existing conflicting bucket settings cause a migration failure instead of silently changing them. User uploads require a fresh reservation, cannot overwrite/delete existing objects, and use normal authenticated sessions. Do not make these buckets public or replace their restrictive policies. Payment proof access ends after confirmed + 30 days; invoice images are retained with expense history. Unfinished reservations are queued after 24 hours. Allow up to one minute for queuing and the five-minute cleanup interval for physical deletion; outages retry with capped backoff. Previously issued signed links last up to 60 seconds.

Run `npm run db:cron:install` before `npm run db:storage:install`. The Storage installer validates the server-only `SUPABASE_SECRET_KEY`, checks that client roles cannot read `vault.decrypted_secrets`, enables the HTTP extension, stores the key and project origin in encrypted Supabase Vault, then schedules cleanup. Run it again when rotating the key. It never prints credentials. `npm run db:storage:verify` creates one randomly named test image and one infrastructure queue entry, checks anonymous denial, executes the real worker, confirms the image is gone, and removes its own test queue entry. It does not create Auth users or change business records. Browser sender/receiver/admin uploads and viewing must still be accepted separately.

Realtime: migration `202611220010_polls_notifications.sql` publishes polls, options, votes and notifications when the `supabase_realtime` publication exists. Its row policies authorize subscriptions; no anonymous policy is added. Websocket delivery still requires browser verification. Native sharing requires user interaction and platform support, with clipboard fallback; no Messenger Page credentials are required for group sharing.

Database TLS: migration commands verify both CA and hostname using the public Supabase root in `supabase/certs/prod-ca-2021.crt`. `npm run db:verify` executes real PostgreSQL role/financial checks in a transaction and always rolls it back. It uses two existing verified Auth identities; it does not create users or send messages. It briefly writes temporary fixture records (including a temporary bank profile) inside that uncommitted transaction, then verifies counts and Auth users are unchanged. Run it during a quiet period so concurrent application writes do not invalidate its count comparison. Database credentials belong only in local/CI maintenance secrets, never public variables or AI tools.

VietQR: configure `NEXT_PUBLIC_VIETQR_TEMPLATE` with an operator-owned production Quick Link template after reviewing current provider requirements. Account numbers over 19 characters, amounts over 13 digits, an unset template, or an unavailable image use the copy-details fallback. `3T-{ref_code}` is a stable payment reference prefix regardless of the UI app name. The receiver must check their bank statement and manually confirm receipt; QR generation never changes payment status. Source: https://www.vietqr.io/qr-dong.
