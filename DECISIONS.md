# Decisions

- New owner direction: invite-first onboarding and minimal UI. Authenticated users without any active group membership see only `/welcome`, with invitation guidance and logout. Protected page URLs redirect there and feature POST/API calls return 403; failed membership checks fail closed with 503. Login, OAuth callback, invitation acceptance and secret-protected cron routes remain available. The first valid invitation unlocks features, and removal from the last group restores the waiting page. This gate supplements the existing per-group RPC/RLS authority checks. There is no non-member super-admin UI exception.
- Home prioritizes two personal balances, the next session and one create-session CTA. Secondary utilities live under “Thêm” on desktop and in the profile on mobile; recent history and session editing/proposal forms expand on demand. The anonymous demo dashboard and quick calculator are removed from the entry flow. Newcomers see no sidebar, bottom tabs or feature links.

- Application identity defaults to `NEXT_PUBLIC_APP_NAME=3T`. UI language is Vietnamese; calendar display uses Asia/Ho_Chi_Minh.
- Money uses bigint internally. API monetary fields must be decimal strings. Live money queries must use text projections, not JSON numbers.
- Hamilton allocation rounds absolute amounts in 1,000 VND units and reapplies the sign. Member IDs break ties deterministically. The payer receives the sub-unit remainder when included.
- Reconciliation subtracts confirmed cash flows from new economic balances. Confirmed records are immutable.
- Database writes are denied by default. The initial payment RPC checks both active membership and the exact sender/receiver. Admin fallback is not enabled until its request age and public-reason checks are implemented.
- Current migration is an initial foundation, not the full handoff schema. Do not treat it as completion of the eight milestones.
- Supabase authentication uses server-side cookies, verified identity, and the current Next.js proxy convention.
- Anonymous landing data is explicitly labeled demonstration data. The calculator is local and creates no payment obligations.
- AI remains disabled: provider configuration, approval workflows, and live evaluation are not yet implemented.
- Meta Send API documentation describes individual Page-scoped recipients. No official group @bot route was found. Group integration will use sharing; DM requires Page/app credentials and App Review. Sources: https://developers.facebook.com/documentation/business-messaging/messenger-platform/send-messages and https://developers.facebook.com/docs/messenger-platform/getting-started/quick-start.
- Portable Node runtime is ignored under `.tools`. npm lockfile records resolved package versions.
- Group creation uses a dedicated service-role-only provisioning RPC, called exclusively after a fresh server-side verified-email check against SUPER_ADMIN_EMAILS. This client is not available to AI tools. Group membership, invitations and role changes use the actor's JWT and guarded database functions.
- Generic invitations create a fresh membership. Claiming a guest member requires admin approval; the guest ID and its financial history remain intact. If the fresh membership already has session/financial references, automatic merging is rejected to avoid dropping history. An admin cannot claim while retaining the admin role of the fresh membership.
- The last active admin cannot be demoted or removed. A removed user cannot rejoin with a generic invite. Admin changes serialize on the group row; invitation acceptance locks the invitation row before consuming a use.
- Approval requests now include the `member_claim` type. Payload hashes are computed in PostgreSQL, approvals expire after 72 hours, and decisions require an active group admin. Other approval types remain unimplemented.
- PGlite runs actual PostgreSQL RLS and migration tests with Auth role fixtures. The initial pgcrypto extension declaration is omitted in the embedded harness because it is unused by tested migrations; hosted integration still requires separate verification.
- Session accounting RPCs are authoritative. TypeScript previews use bigint and scaled integer ratios; SQL uses exact numeric arithmetic. Golden tests compare both implementations for discounts, fractional percentages, zero shares and sub-thousand remainders.
- Per-person totals use the number of selected beneficiaries, independent of weighting. Exact inputs express nonnegative absolute shares (including discounts); their sum must equal the absolute total before the shared rounding rule. Zero total exact splits use equal zero allocations.
- Planned sessions produce no payment obligations before the collector finalizes the played session. RSVP can only change the authenticated member before the server deadline. Collector claims require bank details and a session-row lock. Collector changes, nominations and admin fallback remain unavailable pending their approval workflows.
- Every payment status change increments session revision, including partial receipts; retries by the same authorized sender/receiver are idempotent. This invalidates stale financial previews.
- Attendance/weight changes and soft expense deletion are previewed inside a PostgreSQL subtransaction that is explicitly rolled back. Saving revalidates the same inputs, authority and revision. Confirmed transfers are preserved; remaining balances route through the collector.
- Court beneficiaries follow attendance. Extra beneficiaries remain explicit; adding a person does not automatically charge them for prior extras. Removing a beneficiary of an exact/percent or single-beneficiary extra is blocked until the collector resolves that extra. Per-person totals are updated when a beneficiary is removed. The last attendee cannot be removed.
- Technical amount entry limit is 1,000,000,000,000 VND per unit/total, with at most 100 beneficiaries and 200 active/proposed expenses. All transmitted monetary values are decimal strings.
- VietQR documentation checked on 2026-11-22 requires an operator-owned template for production Quick Links. `NEXT_PUBLIC_VIETQR_TEMPLATE` enables the image; without it, or for unsupported account/amount formats or image failures, users copy bank details, amount and reference. No paid account is provisioned automatically. Source: https://www.vietqr.io/qr-dong.
- Session requests now support join, leave, weight, shared expense proposals and collector nomination. Inputs bind attendance changes to the requester's own member ID. The current collector decides attendance and expense requests; creator/admin status alone grants no financial approval right.
- The exact expense writer is shared by collector entries, participant-only entries and approved proposals. A shared proposal is fully validated in a rolled-back subtransaction, then saved as `proposed` without allocations or settlements. Approval activates the original expense ID and retains the requester's authorship.
- Requests bind canonical JSON payload hashes and session revision. A changed session requires withdrawal and resubmission; approval does not silently apply to a different financial baseline. Multiple expense proposals are allowed, but one pending attendance request per type/person/session avoids duplicate requests. The internal creator enforces 20 requests per user per rolling 24 hours.
- Existing collector changes require two distinct authorizations: current-collector consent (when a creator initiates the nomination), then nominee acceptance. Consent changes the payload phase and hash without assigning the role. The nominee needs bank details; acceptance changes court advances and reconciles confirmed cash flows in one transaction. A rejected nomination preserves the current collector.
- Requests expire after 72 hours and never auto-approve. Expense proposals are marked rejected when expired requests are cleaned during the next expense submission. Withdrawal retains business history and audit records. Scheduled expiration/notifications and the 72-hour admin fallback still need implementation.
- Approval previews use rollback subtransactions. Decisions are rechecked for active group membership, current authority, expiry, payload hash, baseline revision and session lock; approved requests cannot execute twice. The model has no approval tool because AI integration remains disabled.
- Hosted migration completed on 2026-11-22: 10 migrations, 13 RLS-protected public tables, 2 existing Auth users preserved. Preflight confirmed no existing public business tables, custom functions, views or migration history. All files were applied in one transaction, with Supabase-compatible migration history and a separate checksum ledger in the private migration schema.
- Migration tooling uses `SUPABASE_DB_URL` only for maintenance commands. It matches the database to the configured API project, verifies TLS using Supabase's public root CA, serializes migration runs with an advisory transaction lock, and refuses changed applied files or unknown remote history. No connection secrets are logged or passed as shell arguments.
- Hosted verification exercises actual PostgreSQL client roles, proposals, confirmed transfers and refunds using existing verified Auth identities; all fixture writes are rolled back. This validates the hosted SQL path and does not claim browser/Auth-provider, Storage, Realtime or concurrent execution acceptance.
- Polls allow 1–24 slots and 1–100 minimum yes votes. Deadlines must precede the first slot. Votes bind the current member, removed members do not count, and closing is serialized/idempotent. Votes seed intentions only; commitments remain explicit self actions. A creator/admin may close an expired poll if the chosen slot is still in the future.
- Recurrence is weekly in Vietnam's fixed UTC+7 timezone, bounded to 1–12 subsequent weeks, materialized up to 28 days ahead. Instances are unique by series/start and always start without a collector or commitments. Stopping a series prevents future materialization and preserves existing sessions. Removed series creators stop generating new instances.
- In-app notifications use unique recipient/event keys. Scheduled reminders follow the handoff stages; missed stages are not replayed as a burst. Payment notifications never confirm receipts. Deadline processing records system-authored auto-not-going events; system events now permit a null actor ID. Approval/settlement triggers also notify on real business changes; rolled-back previews emit no persistent notifications.
- Hosted pg_cron was enabled using official Supabase installation guidance, and the app-owned job `3t-minute-maintenance` has verified successful executions. Maintenance functions are inaccessible to client roles. Seven-day retention applies only to this job's infrastructure logs, not business audit history. Web Push, receipt cleanup and actual admin fallback execution remain pending.
- Realtime publishes only polling and notification tables in this milestone; subscriptions use the user's JWT/RLS. A 30-second visible-tab refresh and focus refresh cover websocket failures. Browser delivery still requires acceptance testing. Messenger group integration is user-triggered Web Share/clipboard, without bank data or unofficial account automation.
- Receipt milestone supersedes the earlier pending-storage status: 18 migrations are now hosted, with 21 RLS-protected public tables and two private image-only buckets. Existing applied migrations remain immutable.
- Payment evidence and expense invoices use separate tables/buckets because their readers differ. Only active sender, receiver and group admin read payment proofs; group members read invoice images. Uploads require a generated path, uploader-owned 15-minute reservation, appropriate business authority, 2 MiB limit, allowed image MIME and no overwrite/delete. Restrictive Storage policies preserve these limits even if an unrelated broad policy exists.
- The browser re-encodes images as JPEG (maximum 1600px) before upload, removing source metadata. The server checks image signatures before normal finalization; SQL checks Storage metadata and authority. Authenticated users can call finalization RPCs directly, so supported MIME restrictions and private delivery remain the database boundary. The service secret is never used by user upload/read actions. Image views use 60-second signed URLs.
- Payment proof files lose access at confirmed + 30 days independently of cron. The minute job queues expired files and abandoned reservations after 24 hours; a separate five-minute worker deletes through the official Storage API. Leases and bounded retries tolerate failures. Invoice files remain with expense history, while abandoned invoice reservations are cleaned. Evidence rows, references, notes and payment/audit history remain; upload never changes payment status.
- Cleanup credentials live in encrypted Supabase Vault, configured from the local server secret using bound SQL parameters. The installer refuses client-readable decrypted secrets. Private SQL workers use the HTTP extension with connection/overall timeouts and an advisory lock. Actual API deletion and anonymous denial were verified using only a generated disposable fixture; cron runs also succeeded. Browser receipt acceptance remains outstanding.
- Calendar management adds migrations 018–019, bringing the hosted total to 20 without adding public tables. Creator, collector and group admin authority is checked under a session-row lock, independently of financial authority. The RPC accepts only whitelisted calendar fields, requires a reason and the current revision, writes before/after audit data, and notifies the group. No-op edits leave revisions and notifications unchanged.
- To preserve self commitment and existing obligations, changing start/deadline is allowed only while planned and before the original deadline, with the new deadline still in the future. Descriptive metadata remains editable later until the 30-day settled lock. Any schedule change resets current choices, appends their prior values to attendance history, and requires fresh self confirmation. This conservative restriction prevents moving a closed deadline forward to evade obligations. UI inputs retain original timestamp precision when unchanged.
- Calendar cancellation is limited to sessions with no nonzero expense history (including rejected/deleted proposals), no transfer history and no nonzero allocations. It preserves business rows, cancels pending requests, clears nominations, and affects only the selected weekly instance. Reopening requires a future deadline, restores planned status and resets choices; it never confirms attendance or payments. Sessions with money must use the collector's financial adjustment flows instead.
- A schedule generation increments only for rescheduling/reopening. Commitment/play reminder deduplication includes this generation, while generation zero retains the preexisting keys so migrating unchanged sessions does not resend old reminders. Financial and normal RSVP revisions do not restart reminder stages. Supabase Cron continues to run the private maintenance wrapper with receipt expiry.
- Milestones 1–2: migration 020 adds a private RLS-protected super admin allowlist and group-creation request records. The runtime group RPC uses the current user's JWT, verified canonical Auth email and active database allowlist entry. The old provisioning helper is database-owner-only; the service role can no longer invoke it. Super admin status grants no general group-reading bypass. Deployment synchronization reads `SUPER_ADMIN_EMAILS`, validates/normalizes it, applies additions/revocations atomically and prints counts only. Empty lists require an explicit CLI flag; removed entries remain inactive records.
- Group creation locks the verified identity and allowlist entry, serializes the actor/request key, hashes the normalized payload, and commits one group/admin/audit result. Retries check current authority again and return the original group only for matching payloads. Client keys are scoped to the actor. This is the first idempotent command; financial commands and recalculation batch links are still pending. A real two-connection rollback test verifies blocked retries and recovery without persisted business fixtures; the full concurrency matrix is not yet accepted.
- Dependency manifests now pin the exact versions already resolved in the lockfile; no upgrades were performed in this change. CI now runs production build as well as typecheck/lint/tests. Remote CI execution remains to be verified.
- The user explicitly requested a later UI/layout redesign. Track it in milestone 7 together with shadcn/ui, Be Vietnam Pro, consistent navigation/theme, accessibility and PWA work. Until then, change UI only as needed to expose business workflows. The eight-milestone acceptance checklist is maintained in `docs/implementation-status.md`; partial feature commits do not imply milestone completion.
- Milestone 1, migrations 021–022: immutable `session_recalculations` records preserve before/after allocation/settlement snapshots, the previous batch and revision range. Existing reconciliation arithmetic remains unchanged. Issuing and cancelling links are written only on unconfirmed rows; previously confirmed history is never updated/backfilled. The session row serializes the chain, and audit snapshots carry the batch ID. Client roles can only read batches within their active groups.
- Seven financial commands share a private durable result ledger keyed by actor/request UUID. The gateway validates shape, membership and payload hash, serializes matching requests, then delegates new execution to the original private authority-checking cores. Success and its receipt commit atomically. Failed execution reserves no result. A successful replay returns its original acknowledgement without executing again; it requires current active membership and conveys no new authority. A new key must still pass revision/hash/expiry/authority checks. The UI refreshes current state after acknowledgement.
- UI forms retain an intent key while their submitted fields stay unchanged; server actions use the same command service intended for future AI integration. Legacy SQL signatures remain available through deterministic payload keys, including the reviewed revision. Explicit keys distinguish deliberately identical proposals. Poll-to-session creation bypasses client retry keys under its own existing poll lock/idempotency, so independent identical polls remain separate. Financial/approval previews call private cores inside rollback subtransactions, independent of durable retry receipts.
- Embedded and hosted checks confirm no duplicate proposal/approval effects, changed-payload rejection, stale-new-request rejection, batch linkage, preview rollback and immutable confirmed rows. Browser retry acceptance and the full simultaneous financial-operation matrix remain outstanding; milestone 1 is not yet fully accepted.
- Concurrency acceptance now runs nine deterministic overlapping transaction scenarios on a disposable official PostgreSQL 17 container. The runner observes blocked locks before releasing the first transaction, verifies both confirmation/recalculation orders and commit/rollback retry recovery, and removes only its labelled container. It never reads `.env` or connects to hosted Supabase. CI includes this suite. PostgreSQL image source: https://hub.docker.com/_/postgres.
- Migration 023 rechecks invite validity/revocation first, returns the group for an already active member before checking remaining capacity, and consumes capacity only for a new join. This permits retry after winning the last slot without admitting a new member or bypassing revocation/expiry.
- Milestone 2, migration 024: guest-member bank accounts are separate from user profiles, readable only within the active group while the member remains an active unlinked guest. Admin-only writes require a reason and append public audit entries/notifications without putting raw account numbers in audit payloads. Recipient bank reads use the guest record only when no user is linked; claim immediately switches to the user's own profile, without silently copying or retaining the old guest account as a fallback. Updates/claim share the group/member lock order.
- Milestone 3, migrations 025–027: admin financial authority is scoped to an owner-only transaction context table, not caller-set flags or impersonation. A reason and a fresh 15-minute preview are mandatory; apply rechecks membership, admin role, eligibility, source hash and session revision. Approved previews replay without another write. Preview changes roll back. Missing/unlinked collectors permit fallback; a linked collector needs an expired unanswered request addressed to that current collector after 72 hours. Registered collector receipt escalation requires a marked payment older than 72 hours. Guest-receiver confirmations require an explicit statement check; an admin cannot confirm a registered refund recipient's payment.
- Expired requests are preserved and a fresh app request is reviewed/created against current data. Shared proposals create a new expense with the original author instead of reviving the rejected expense. Current requester/nominee membership and the 200-expense cap are rechecked. Nominees still accept separately; new ordinary requests retain the 72-hour lifetime. Admin preview drafts expire after 15 minutes and are excluded from 72-hour escalations/ordinary approval UI notifications.
- Unlocking an old settled session is admin-only, requires a public reason and lasts 24 hours. The original settled/confirmation timestamps remain intact; unlock changes the lock condition without granting financial authority. Core writers, calendar and invoice-upload guards honor this window. Group/member/session lock order for fallback and guest banking uses group NO KEY UPDATE to remain compatible with financial foreign-key checks. Eleven actual PostgreSQL races pass, including source withdrawal after preview and concurrent guest-bank changes.
- Milestone 3, migrations 028–029: group categories/templates are seeded automatically, admin-managed and archived rather than deleted. Template amounts and expense editor inputs use decimal strings. The idempotent `save_expense` command uses the existing exact writer for create/edit, retaining expense IDs, authors and receipt references. Shared active expenses require collector authority or an eligible reviewed admin context; participants can edit pending proposals or their own self-only active expenses. Court edits always use the current collector, all current attendees and weighted splitting.
- Proposal edits are validated in a rollback subtransaction and refresh canonical payload/hash/revision/expiry without financial effect. The baseline revision is included in the payload hash so an unchanged proposal rebased onto new finances invalidates the old review. Active edits recalculate against confirmed cash flows. Client financial reviews are tied to the submitted payload/revision, including court finalization, so refreshed data cannot silently keep an old reviewed flag.

The proposed dedicated SMTP sending subdomain is `auth.thichtinhtien.online`; provider-issued DNS records still need verification.

- Decision routing is opt-in per group and uses that group's encrypted OpenRouter credential outside business tools. Only two verified free Perplexity decision IDs are configurable. Classification can choose a read path or a tool family, never elevate authority. Debt answers are computed/formatted from JWT-protected data; payment messages resolve a unique existing obligation in code and create normal app-confirmed drafts. Model failure/low confidence preserves conservative tool discovery. Direct code paths count decision usage in the same AI run and avoid chat generation where possible. A local Auth/HTTP integration check uses mirrored ciphertext and synthetic business fixtures; it never writes hosted business data or sends email.
