# 3T — Thích Tính Tiền

Vietnamese sports group expense tracker. **Implementation in progress; not ready for real financial records.**

## Local development

Use Node.js 24 LTS. Run `npm ci`, `npm run dev`, then visit http://localhost:3000. Copy `.env.example` to `.env` only when an environment file does not already exist. Never commit credentials.

Commands: `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:concurrency` (Docker), `npm run build`, `npm run security:check`. After a production build, `npm run test:pwa` uses Playwright Chromium (`npx playwright install chromium`). If browsers are installed in `.tools/browsers`, set `PLAYWRIGHT_BROWSERS_PATH` to that absolute directory.

Hosted database: all 39 migrations were applied on 2026-11-22; all 28 public tables have RLS. Hosted permission/accounting/scheduling smoke checks run in a rolled-back transaction, preserving existing Auth users and leaving no test business data. `npm run db:status` inspects migration state; `npm run db:migrate` applies new files atomically; `npm run db:verify` reruns the rollback-only checks. The website and remaining features are not yet deployed or fully accepted.

The app uses a shared sidebar/five-tab mobile layout, self-hosted Be Vietnam Pro, persistent dark mode, a native keyboard-accessible calculator dialog, loading/error states and offline recovery. `/me` includes install instructions and push controls. The worker caches only public fallback HTML/icon assets, never authenticated pages or payment responses. The browser suite covers 320–1440px, dark mode, dialog focus, manifest icons, offline fallback and recovery.

Group management: `/groups` lists memberships and exposes group creation only to the verified super admin. Group pages support expiring/revocable invitations, member roles, soft removal, and admin-approved claims of existing guest members. `/me` saves private bank/profile information. Invite destinations survive Google and email authentication; return URLs are allowlisted.

Group creation now uses the user's JWT. Both server configuration and a private database allowlist check the verified identity; clients cannot provision an arbitrary owner through a service-role helper. `npm run db:admins` previews allowlist counts; `npm run db:admins:sync` synchronizes `SUPER_ADMIN_EMAILS` atomically. Repeated group submissions with the same actor/request key return the original group and reject changed payloads. `npm run db:verify:group-retry` uses two PostgreSQL connections to verify waiting/retry after rollback without persisted fixture data. The two-connection test covers group creation only; the full concurrency matrix remains pending.

Financial commands now use `execute_financial_command` with an actor-scoped request key and payload hash. The UI/service cover session creation, collector claim, court finalization, expense submission/proposals, attendance/expense corrections, payment actions and approval decisions. Successful retries acknowledge the original result without another write; changed payloads are rejected, and a new request cannot bypass an old revision. Private cores retain the business authority checks. Legacy RPC signatures route through the same ledger using deterministic keys; explicit keys distinguish intentionally identical proposals. Preview transactions call private cores and roll back all writes.

`session_recalculations` records immutable before/after snapshots, revision ranges and previous-batch links. New/replaced transfers link to their issuing/cancelling batch; existing confirmed rows are never backfilled or modified. A replay acknowledges a past command, so the UI refreshes current data afterwards. Active membership is required even on replay. This does not yet establish the full concurrency or browser acceptance matrix.

Tests now execute migrations and RLS against embedded PostgreSQL (PGlite) with a minimal Supabase Auth identity fixture. This exercises database permissions and transactions without Docker; it does not replace hosted Auth, Storage, Realtime, concurrency, or full permission-matrix acceptance tests.

Sessions: `/sessions/new` creates played sessions with reviewed allocation previews or future sessions with self RSVP. `/sessions/[id]` supports claiming an unassigned collector role, finalizing attendance, expense breakdowns, collector-entered extras/discounts with all four split modes, and sender/receiver payment actions. Collector changes to attendance, weights and expense deletion have database-backed previews that roll back all writes, followed by an explicit save against the reviewed revision. Confirmed transfers remain immutable and corrections create new collections/refunds.

Calendar management: the creator, current collector or group admin can edit the title, venue and general note with a reason. Changing start/deadline is permitted only for planned sessions before the original deadline, with a future new deadline; existing RSVP choices reset and members must self-confirm again. Reminder stages are deduplicated per schedule generation, preserving existing reminder keys for unchanged sessions. Sessions with any nonzero expense history or any transfer cannot be cancelled through calendar management. Money-free cancellation preserves history and cancels pending requests; reopening requires a future deadline and fresh self commitments. Changes apply to one weekly instance, notify the group, and check the session revision. Settled sessions older than 30 days require a time-limited admin unlock.

`/debts` and the home totals read actual personal settlements with money encoded as decimal strings. Payment screens show recipient bank details and copy buttons. QR images require an operator-owned VietQR template; see `.env.example` and DEPLOY.md.

Approvals: `/approvals` lists pending session requests addressed to the current member and requests they sent. Attendance/weight requests and shared expense proposals require the current collector's explicit app approval against a preview, immutable payload hash and session revision. Participant-only extras activate directly. Collector nomination requires the existing collector's consent when initiated by the session creator, followed by the nominee's separate acceptance with bank details. Confirmed payments are preserved when collection responsibility moves. Requests expire after 72 hours, can be rejected or withdrawn, and are rate limited to 20 per user per day. History includes actor names and attendance events.

Scheduling: `/polls` creates multi-slot polls; votes are updated under the voter's identity. Creators/admins close a qualifying slot exactly once, producing a planned session with no collector and no automatic attendance commitments. `/notifications` is private to the recipient. Polls/notifications subscribe to Supabase Realtime with focus/30-second refresh fallback. Session and poll pages offer native sharing/clipboard fallback for Messenger without bank data.

Weekly sessions generate up to four weeks ahead, for 1–12 configured weeks; new instances have no collector or committed attendees. The hosted `3t-minute-maintenance` cron runs every minute for deadline finalization, reminder schedules, request expiry, weekly generation, admin escalation and receipt expiry. `npm run db:cron` shows both jobs and latest runs; `npm run db:cron:install` installs the minute job. Web Push subscriptions, queue/retries and per-payment reminders are implemented; production delivery still requires deployment and device acceptance.

Receipts: senders can attach payment screenshots, transaction references or notes; expense authors/collectors can attach invoices. Images are resized/re-encoded in the browser and uploaded using the user's Storage permissions to private image-only buckets (2 MiB limit). Proofs are readable only by active sender/receiver/group admins; invoices by group members. Viewing uses 60-second signed links. Proof images become inaccessible 30 days after confirmation and are queued for physical deletion; business metadata remains. Uploading evidence never confirms payment. Abandoned upload reservations expire after 24 hours. The hosted `3t-storage-cleanup` job deletes queued objects through Storage API every five minutes, with leases/retries and credentials in Supabase Vault. `npm run db:storage:install` configures it; `npm run db:storage:verify` uploads/removes one generated fixture to check actual API deletion and anonymous denial. Storage API cleanup has been verified; browser upload acceptance remains pending.

AI uses encrypted per-group credentials, JWT business tools and app-reviewed drafts. Free OpenRouter Decisions handles debt reads and reviewed payment drafts directly; other intents can use the group's chat model. `npm run ai:eval:decisions:full` is a classification benchmark, separate from the full tool/parameter eval. Chat free quota currently blocks full provider acceptance. `npm run ai:verify:runtime -- --browser` tests local Supabase Auth, actual decision routing, twelve authenticated pages and creation of a ten-member played session with allocation checks. It mirrors only the dedicated test group's encrypted credential; business fixtures remain local.

Shared forms/profile/loading use shadcn/ui components with the 3T palette and 44px buttons. `npm run test:auth-ui` verifies profile persistence, responsive dark mode and logout against local Supabase without AI calls. Provider diagnostics support Gemini with a default 15,000-token budget; incomplete runs never pass acceptance.

`npm run test:payment-ui` checks browser receipt uploads, private file permissions, safe retry after a lost committed response, server-confirmed receipt of funds, stale-preview rejection, a post-collection refund and collector handover. It uses only local fixtures and no LLM. Local Supabase must be migrated and Playwright Chromium installed; screenshots/logs stay in `.tools/payment-ui`.

Pending: full permission/tool eval acceptance, remaining UI flow/accessibility checks, production OAuth/SMTP, push/Realtime on real devices, and hosted website deployment. Stale requests must be withdrawn and resubmitted; they are not silently rebased. The canonical requirements are in `docs/handoff_prompt.md`; milestone progress and acceptance gaps are tracked in [docs/implementation-status.md](docs/implementation-status.md).
